# Blocking deleted devices with `pki.blocklist` — design (2026-11-28, before code)

> **Status (2026-11-28, after the code):** built as below, with one change found in review (a node holds at most 16 unexpired certs; a renewal over that gets 429). What was built, measured and is not covered: [[concepts/deleted-devices]]. This note keeps what was decided before the code.

Item 14 of the plan approved on 2026-11-27: "Today a deleted device can rejoin
until its cert expires, up to 24 hours." `TestE2E_DeletedPeer` pins it as a
known gap: a device deleted in the dashboard keeps a valid cert (24 h, plus the
1 h of clock-skew tolerance of patch 25), and every agent and the server's
lighthouse still accept it, because nothing tells them.

## What Nebula offers (v1.11.2 as vendored; to be shown by a spike first)

- `pki.blocklist`: a list of cert fingerprints (lowercase hex sha256 of the
  cert's binary body). Read in `loadCAPoolFromConfig`; a reload builds a new
  CA pool, with no "has changed" gate, so adding and removing both work.
- A handshake from or to a blocklisted cert fails on both sides.
- An open tunnel with a blocklisted peer is closed at its next
  connection-manager tick (`isInvalidCertificate`, `connection_alive_interval`,
  10 s for our agents), whatever `pki.disconnect_invalid` says.
- The lighthouse checks nothing about the host it is asked for; it only stops
  answering once it holds no tunnel with that host.

## Design

1. **The server records every cert it issues.** New table `node_certs`
   (migration 013): `fingerprint` (primary key), `network_id` (references
   networks, cascade), `node_id` (no reference: the row must outlive the node),
   `not_after`. Written in the same transaction as the node's cert, in the
   three store methods that write one (`Create`, `CompleteEnrollment`,
   `UpdateCert`), so no path that issues a cert can forget it. Rows whose
   `not_after` is more than the skew tolerance in the past are removed when a
   cert is recorded and at start.
   - Certs issued before migration 013: at start the server records the cert
     each node holds now. Older certs of the same node (renewed in the last
     24 h) are not known; they expire within a day. Documented.
2. **A network's blocklist** is the fingerprints of its `node_certs` rows whose
   node no longer exists and whose `not_after` + skew tolerance is still ahead.
   Every path that deletes a node (API, prune, a DELETE by hand) is covered,
   because the list is derived from the absence of the node row.
3. **Delivery: the heartbeat answer** carries `blocklist: [{fingerprint,
   until}]` for the device's network, present (maybe empty) whenever the server
   knows the feature. Absent: the agent keeps what it has. Bounded (4096
   entries); each entry checked (64 lowercase hex, `until` a time).
4. **The agent keeps the list in `<enrollment dir>/blocklist.json`** and puts
   it into `pki.blocklist` of the config it loads (like the "Block incoming"
   overlay; `nebula.yaml` is not written). A changed list is applied by an
   in-place reload with the P2 machinery (start lock, `lockNebulaYAML`, the
   loaded text with only `pki.blocklist` changed). Entries past `until` are
   dropped. The agent never blocks its own cert fingerprint (a server bug must
   not cut a device off its own network). The comparison of the loaded text
   with the file (`sameApartFromFirewall`) must ignore `pki.blocklist`, or
   every firewall apply would wait forever.
5. **The server's lighthouse** gets the same list, by an in-place reload of its
   own config, when a node is deleted and in its 30 s loop; and at every start.
   So a deleted device learns no addresses and gets no relay.
6. **Order on start-up:** the cached list is in place before Nebula starts, so
   a restart opens no window.

## What it does not cover (documented, not fixed here)

- Agents of v0.11.31 and older ignore the field and keep accepting the device
  until its cert expires.
- `hop client join` devices have no heartbeat and get no list.
- A device that was offline while the node was deleted accepts it from its
  start until its first heartbeat answer, unless its cache already has it.
- Agents learn within one heartbeat (60 s ± 10 %) plus one tick (10 s).
- A cert stolen from a device that is not deleted is not revoked: that needs a
  "revoke this cert" action, a product decision of its own.

## Tests (red first)

- Spike, `internal/client`, two real peers: a's in-place reload with b's
  fingerprint in `pki.blocklist` closes the tunnel within a tick and refuses a
  new handshake; removing it lets b back.
- `internal/api` against the real server: the heartbeat answer has the list
  after a delete (API, prune), not for other networks, not for live nodes, not
  for expired certs; a renewal records the new fingerprint; the backfill at
  start.
- `internal/client` e2e: the list from a heartbeat blocks b, survives a
  restart (cache), drops expired entries, ignores its own fingerprint, refuses
  a bad list; firewall applies still work with a list in place.
- `cmd/agent`'s `TestE2E_DeletedPeer` turns from a known gap into a test that
  the deleted device is cut off within one heartbeat plus a tick and stays out.
- The lighthouse: a deleted device can no longer ask it for addresses.
